架构重构方案 · v1.0

班级工作台 2.0
教师端 / 学生端双端架构

以教师机为唯一服务端与数据源，一套进程同时承载教师端与学生端网页；学生端启动即拿到教师端下发的功能开关与数据投影；双击一个入口完成启动，适配无外网、单交换机、机房还原卡等真实校园网络环境。

分析对象：3 个发行包（通用 / win-x64 / mac-arm） 代码规模：主程序 30,513 行 · 服务端 3,683 行 基线日期：2026-10-30

方案摘要：四个决定性的取舍

DECISION 01 数据主权从浏览器搬到教师机 业务数据改存教师机 SQLite，浏览器只做缓存。这是“学生端能同步到数据”的唯一前提——现在数据被密码加密锁在老师那台电脑的 localStorage 里，任何外部端都读不到。
DECISION 02 一套进程、一个端口、两套前端 不新增第二个服务。教师端页面沿用现有单文件应用（改造数据层），学生端新写一个轻量 SPA，同源同端口下发，端口固定 8080，避免任何跨域与多端口运维。
DECISION 03 学生端是“投影”，不是“副本” 学生端不同步整库，只同步与本班/本人相关的字段投影；写操作走白名单动作。安全边界放在服务端，而不是靠前端隐藏。
DECISION 04 复用已有行级同步引擎，不重写 主程序里已有一套按行 diff、带墓碑和表字段白名单的同步引擎（24 张表），目前因“纯本地模式”被停用。把它从 Supabase 改成指向本机服务端，改造量远小于重做。

01现状体检：三个结构性事实

先看清楚现在这套东西是什么，才能判断哪些能留、哪些必须动。

1.1 文件构成

文件规模当前角色双端架构下的处置

submission-system/server.py1,043 行标准库 HTTP 服务：静态托管 + 学生提交 API + 局域网 IP 探测升级为唯一服务端

quickform-server/Flask 应用，含便携运行时“活动任务 / 收集表”独立服务，占 5055 端口降级为可选插件

1.2 事实一：服务端是空壳，业务数据全在浏览器里

这是整件事的根因。主程序把 24 张业务表写进 localStorage 的 wb-db-* 键，并用「本地密码 → PBKDF2（15 万次）→ AES-256-CBC + HMAC」加密。密钥只存在于老师那次会话的内存里，服务端进程、学生设备、乃至老师换一台电脑，都拿不到明文。

// index.html:7574  —— 渲染层所有读写都从这里进
function dbT(key) { ... return DB[key]; }        // 返回数组引用
function dbSet(key, val) { DB[key] = arr; dbPersistSoon(); }

// index.html:7614 —— 落盘即加密，服务端永久读不到
LS.set('wb-db-' + k, DATA_KEY_SET ? encStr(json) : json);

结果是：submission-system/ 这个“服务端”只托管静态文件、收学生提交的作品、管课件，它不知道班里有多少人、谁坐在哪、作业是哪几份。学生端因此只能做“交作业”这一件事。

结论：“学生端自动同步教师端的功能与数据”这件事，卡点不在网络、不在前端，而在数据根本没上服务端。不先把数据主权搬过去，双端架构无从谈起。

1.3 事实二：同步引擎已经写好了，只是被关掉了

主程序里有一套完整的行级同步实现，原本面向 Supabase：

能力位置现状
24 张表的字段白名单 + 业务主键合成SYNC_TABLES（8008 行）可用，字段清单与 DB_KEYS 一一对应
稳定行 ID（无 id 的表用业务键合成，如课表、考试成绩）rowIdOf()可用
行指纹去“假改动”rowHash()可用
脏扫描 diff / 增量拉取 / 定时调度syncDiff() syncPullTable() syncSchedule()可用
软删除墓碑deleted 字段贯穿可用
云 SDK 注入与鉴权5728 行起已停用：注释写明“纯本地模式，不再加载云 SDK”

这意味着重构的性价比很高：把传输层从 Supabase REST 换成 /api/v2/sync，把 owner_id 换成“班级 + 角色作用域”，引擎本体（diff、hash、墓碑、幂等）几乎不用重写。

1.4 事实三：学生端已经有壳，但只覆盖一种场景

s/index.html 的五个视图（认人 → 任务列表 → 任务详情 → 提交成功 → 我的提交）已经解决了学生端最难的部分：身份绑定、文件上传、撤回、回执下载。它缺的是“除交作业以外的一切”——不知道今天上什么课、坐哪、作业还剩几份、考了多少分、明天值不值日。

1.5 顺带发现的耦合风险

端口即数据身份

启动器检测到 8080 被占时拒绝自动换端口，因为换端口等于换 localStorage 仓库，老师会看到“数据全没了”。数据上移服务端后，这条约束解除，但端口仍需固定——它变成了学生链接的稳定性问题。

双服务、双端口、双数据目录

QuickForm 跑在 5055，数据在另一个 SQLite，活动作品在第三个目录。双端架构下这种分裂会直接变成“学生端要连两个地址”，必须收敛。

约束为什么怎么做

04教师端 → 学生端同步机制

一句话：服务端是唯一真相，rev 游标做增量，SSE 做实时，"投影"做隔离。

4.1 数据流总览

图 2　一次作业布置到学生手机可见的完整链路（目标 < 300 ms 局域网内）

4.2 标识与游标

  • 行 ID：沿用 rowIdOf() 的规则——有 id 用 id；课表用 day×10⁶ + period×10³ + class，考试成绩用 exam×10⁷ + student×100 + course 合成。两端对同一条记录的指向永远一致，upsert 天然幂等。
  • rev：全局单调递增整数。每次写入在 changelog 表追加一条 (rev, table, row_id, op, ts)，行上同时记 rev。学生端保存 last_rev，重连从游标续传，不重不漏。
  • 墓碑：删除写 deleted=1 并占用一个新 rev，保留 90 天。学生端收到墓碑即从本地移除。
  • 行指纹：rowHash(table,row) 只算白名单字段，服务端存一份，重复推送直接丢弃，避免“改一个字传一整表”。

4.3 三条通道

通道触发时机行为
全量快照首次登录、last_rev=0、游标过期GET /api/v2/sync?since=0，服务端按角色投影后 gzip 返回。50 人班实测约 120 KB，压缩后 35 KB，局域网 < 200 ms
增量拉取收到 SSE 信号 / 轮询到期 / 页面重新可见since=last_rev，返回至多 500 行 + hasMore，循环拉到追平
实时信号教师端任何写操作提交成功后SSE event: rev 只带版本号（十几字节）。断线由浏览器自动重连，服务端补发 Last-Event-ID 之后的版本号
为什么不用 WebSocket：标准库没有 WS 实现，引第三方库违背“零依赖”。SSE 在 ThreadingHTTPServer 上只需一个长连接线程，且自带重连与 Last-Event-ID 语义，正好匹配“只推信号、不推数据”的设计。降级路径：SSE 不可用时自动切 5 秒轮询（学生端 10 秒）。

4.5 写入边界与冲突

谁能写什么

角色写权限
教师端24 张业务表全量 upsert
学生端仅 5 类动作：submission（提交/撤回）、leave_request（请假）、receipt（回执）、read_flag（已读）、profile（主题字号，存本地不入库）

学生写请求一律走独立端点，服务端从会话里取 student_id，忽略请求体里的任何身份字段——前端伪造无效。

冲突处理

  • 教师端多设备并发：按 updated_at 新者胜；若客户端 base_rev 落后且该行已变，服务端返回 conflicts，客户端刷新该行并提示“已被其他设备修改”。
  • 教师 vs 学生：学生只能追加，不产生冲突。
  • 重复提交：Idempotency-Key + 10 分钟去重表，弱网重试不会产生两条记录。

4.6 首次升级：老数据怎么上去

这是最容易被忽略、也最容易出事的一步。老数据被老师本机密码加密，服务端没有密钥，无法自行解密，必须由浏览器解密后“上交”一次。

检测

教师端首次连上新服务端，GET /api/v2/state 返回 empty:true，同时浏览器本地有 wb-db-* → 弹出一次性迁移向导。

解密

输入本机密码，页面用现有 deriveDataKey 派生密钥，读 24 张表 —— 这段逻辑现成，不用改。

上传

POST /api/v2/admin/import 一次性提交全量快照（gzip + CSRF 令牌，仅 127.0.0.1 与已登录教师会话可用）。

校验

服务端逐表比对条数与哈希，返回 {classes:3, students:142, ...}；页面显示“已迁移 24 张表 / 1,284 行”，并自动导出一份服务端备份。

收尾

迁移成功后不再读取本地 wb-db-*（保留不删，作为回滚保险）。此后所有读写走服务端。

不要做的事：不要尝试把 localStorage 的密文直接搬到服务端“以后再解”。密文与老师本机密码、盐值绑死，换机器就永久打不开。迁移必须发生在浏览器里、解密之后。

4.7 加密模型的调整

原来“密码 = 数据加密密钥”，本质是单机防御：防别人拿到这台电脑的文件。改成服务端后，这个模型必须换，但安全性不能降。

层原来现在
服务端数据库不存在SQLite 明文 + 文件系统权限；可选整库加密（导出时可打包加密 zip）
教师端会话本地密码解锁数据服务端口令（PBKDF2-SHA256，12 万次）+ HttpOnly SameSite=Lax Cookie + CSRF Token
浏览器缓存全部业务数据的密文只缓存投影快照，仍用本机密码加密，30 天过期
学生端无不落库；sessionStorage 存会话，关浏览器即失效
备份.cwbackup 加密包服务端 /api/v2/backup 导出同格式加密包，导入仍走浏览器解密 → 服务端写入
一句话原则：服务端负责“谁能看”，密码负责“谁能进”。不要再用一个密码同时承担这两件事——那是单机时代的妥协。

053 万行单文件的改造点

不改渲染层，只换数据层。这是唯一能把风险控制住的做法。

5.1 为什么不能重写界面

index.html 里 17 个视图的渲染函数直接调用 dbT('students') 并把返回的数组当成可变引用（dbT('students').push(...)、.splice()、排序后回写）。重写界面等于重做 30,512 行里 80% 的逻辑，还要重新踩一遍考勤、蛇形排座、德育批量、课表周次这些业务坑。

所以策略是：保持 dbT() 的签名与引用语义不变，只在它下面换掉存储介质。

5.2 需要动的 6 个函数

位置现状改法
dbT(key) 7574返回内存 DB[key]不动。内存镜像由同步层填充
dbSet(key,val) 7589整表替换 + 落盘加一行 NetSync.markDirty(key)；原 dbPersistSoon 保留做本地缓存
dbPersist() 7614写 localStorage 密文改为“写缓存快照”，失败不阻断（服务端才是真相）
persistAll()全量落盘同上，并在切换加密状态时触发一次 NetSync.push()
syncDiff / syncPullTable / syncSchedule 8269-8559指向 Supabase REST替换传输实现，保留 diff/hash/墓碑算法；接口改 /api/v2/sync
登录 / 锁屏 151 行起本地密码校验 wb-lock-hash改为服务端 POST /api/v2/auth/login；锁屏 UI 与交互不变

新增一个约 400 行的 netsync.js，挂在 index.html 的 <script> 末尾即可，不侵入主逻辑：

// netsync.js —— 单文件适配器，约 400 行
const NetSync = {
  rev: 0, dirty: new Set(), timer: null, es: null,

  // 启动：先拿快照填满 DB，再开 SSE
  async boot() {
    const snap = await api('/api/v2/sync?since=0&scope=teacher');
    syncApply(snap);              // 复用现有合并逻辑，填充 DB + state.todos
    this.rev = snap.rev;
    this.connect();
  },

  // 脏表 → 按行 diff（复用 syncDiff 的 rowHash/rowIdOf）
  async push() {
    const changes = [];
    for (const k of this.dirty) changes.push({ table: SYNC_KEY_TABLE[k], rows: diffRows(k) });
    const r = await api('/api/v2/sync', { changes, base_rev: this.rev });
    if (r.conflicts.length) handleConflicts(r.conflicts);
    this.rev = r.rev; this.dirty.clear();
  },

  // 只收版本号，收到就去拉增量
  connect() {
    this.es = new EventSource('/api/v2/events?since=' + this.rev);
    this.es.addEventListener('rev', e => {
      if (+e.data > this.rev) this.pull();
    });
  },
};

环境自检（< 1 秒）

Python 版本、文件完整性、data/ 可写、SQLite 可打开。任一失败 → 打印具体原因 + 一句可执行的处置建议，不静默降级。

端口决策

8080 空闲 → 直接用；被占 → 先请求 /api/v2/ping，若返回本项目标识则复用已运行实例（只打开浏览器，不启第二个进程）；否则停下来说明“被谁占了、怎么关”，绝不悄悄换端口。

数据库与迁移

打开 data/workbench.db（WAL 模式）；版本号低于代码则就地升级表结构；首次启动生成班级码与自签口令页。

起服务

ThreadingHTTPServer(('0.0.0.0', 8080))，就绪探针轮询 /api/v2/ping，最多等 20 秒。

打印横幅 + 二维码

探测所有局域网 IP（复用现有 lan_ips()，按 192.168/10/172 排序），生成学生入口二维码，写入 data/entry.txt 便于复制。

打开浏览器

默认开 /teacher/；--no-browser 可关。窗口关闭或 Ctrl+C → 优雅停服、刷盘、写关闭时间。

09风险与取舍

有几件事必须提前说清楚，否则上线后会反复返工。

风险影响应对
加密模型切换导致老数据打不开 高 迁移必须由浏览器解密后上传；迁移前强制导出一份旧备份；迁移成功后保留本地密文 30 天不删，可回滚
3 万行单文件的隐性耦合 中高 只改 6 个函数、保持 dbT() 引用语义；每阶段跑一遍“17 个视图逐页点检”脚本；不做界面级重构
学生端隐私边界被突破 高 投影在服务端白名单实现，不依赖前端；上线前对每个接口做一次越权测试（换 student_id 能否读到他人数据）
教师机关机/休眠 = 全班掉线 中 交付文档明确“教师机是服务端”；电源策略设为不睡眠；启动器检测到电池供电时提示
机房还原卡清掉数据 中 data/ 支持软链接/配置到非还原盘；每日自动快照；首次启动检测“上次数据比今天新”时警告
QuickForm 依赖拖累打包体积 低 降级为可选插件，默认不启动；通用包不再强制捆绑 270 MB 运行时
一个明确的产品取舍：不做“学生端可编辑自己档案”“学生互相可见通讯录”“家长端”。这三件事会立刻把架构从“班级内网工具”推向“需要合规评估的 SaaS”，而收益远小于成本。留出扩展位，但 v1 不实现。
