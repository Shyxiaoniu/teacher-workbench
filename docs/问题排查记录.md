## P-016 · 压缩包解压后「没有权限打开」

**版本**：2.0.16 ｜ **日期**：2026-11-05 ｜ **严重度**：高（阻断启动）

### 现象

- macOS / Linux 用户把发行包 `班级工作台<版本>-<yyMMdd>.zip` 解压后：
  - 双击 `启动工作台.command` → 系统弹「"启动工作台.command"没有权限打开」；
  - 或终端执行 `./启动工作台.command` → `Permission denied`；
  - 用 `ls -l` 看，`.command` / `.sh` 全是 `-rw-r--r--`（644），没有 `x` 位。
- 顶层启动器虽然能双击，但它 `exec` 的 `app/启动教师端.command` 同样报没有权限，
  所以还是起不来。
- Windows 解压不受影响（Windows 不认 Unix 权限位）。

### 触发条件 / 复现步骤

1. 在 **Windows 上**构建发行包（`python tools/make_release.py`）；
2. 把 zip 拷到 **macOS 或 Linux**，用系统解压 / `unzip` / `ditto` 展开；
3. 双击或执行包里任意 `.command` / `.sh` 文件。

> 只解压在 Windows 上打开，永远复现不了；Docker 部署也复现不了
> （Dockerfile 里有 `chmod +x /app/docker-entrypoint.sh`，compose 的 entrypoint
> 又走 `/bin/sh -c`，都不依赖 zip 里的权限位）。

### 原因分析

`tools/make_release.py` 构造 zip 条目时**只**写了权限，没写「这是 Unix 文件」：

```python
zi = zipfile.ZipInfo(path)
zi.external_attr = 0o100755 << 16      # ← 只写了这一半
```

`zipfile.ZipInfo.__init__` 会按平台设 `create_system`：**Windows 上是 0（FAT/MS-DOS）**，
Linux/macOS 上才是 3（Unix）。

而 ZIP 规范里，权限位（`external_attr` 高 16 位的 `st_mode`）只在
`create_system == 3` 时有意义。主流解压器看到 `create_system == 0` 会：

- 忽略高 16 位权限；
- 按 `umask` 给默认权限（普通文件 644）。

于是 `.command` / `.sh` 解压出来全是 644，没有执行位。

**为什么「修过一次还复发」**：早前确实补过 `external_attr = 0o100755 << 16`，
但没补 `create_system`，等于把权限写进了解压器不看的字段里。诊断证据（2.0.15 的包）：

```
条目 88 个｜目录条目 0 个｜文件 88 个
create_system 分布：{'FAT(0)': 88}
启动工作台.command                     mode=0o755 create_system=FAT(0) FAIL
app/启动教师端.command                 mode=0o755 create_system=FAT(0) FAIL
app/启动教师端.sh                      mode=0o755 create_system=FAT(0) FAIL
docker/entrypoint.sh                  mode=0o755 create_system=FAT(0) FAIL
```

模式位是对的，但 88 个条目「文件系统类型」全是 FAT —— 权限等于没写。

### 解决措施

1. `make_release.py` 新增 `_zipinfo(arcname, mode, mtime)` 统一构造条目：
   ```python
   zi = zipfile.ZipInfo(arcname, date_time=mtime or time.localtime()[:6])
   zi.create_system = 3                  # 3 = Unix，权限位才生效
   zi.external_attr = mode << 16         # 高 16 位 = st_mode
   zi.compress_type = zipfile.ZIP_DEFLATED
   ```
   所有条目（含 `发行说明.md`、`启动工作台.bat`、`启动工作台.command`）都走它。
2. 顺手把 `date_time` 设成源文件 mtime（原来不设，解压出来全是 1980-01-01）。
3. **新增构建后自检 `verify_release()`**：逐个条目检查
   - `create_system == 3`；
   - `.command` / `.sh` 为 755，其余 644；
   - 文件名带 UTF-8 标记（bit 11，否则中文乱码）。
   任何一条不合格 → **删除 zip 并让构建失败**，绝不产出坏包。

### 验证

- 重新构建后诊断：`create_system 分布：{'Unix(3)': 88}`，全部 PASS。
- 5 个可执行脚本（`启动工作台.command`、`app/启动教师端.command`、
  `app/启动教师端.sh`、`app/submission-system/run.command`、`docker/entrypoint.sh`）
  的 mode 均为 755，且 shebang 为 LF（无 CRLF）。
- `make_release.py` 若把 `create_system = 3` 去掉，构建会直接报
  「发行包自检失败（已删除产物）」并退非 0 —— 这就是防复发的闸门。

### 防复发

- 自检内建在构建流程里，不依赖人记得检查。
- 诊断脚本 `E:\wb-shots\run_zipperm.py`（计划任务 job `zipperm`）可随时复查任意包。

## P-015 · 自动更新并重启后服务起不来

**版本**：2.0.15 ｜ **日期**：2026-11-05 ｜ **严重度**：致命（服务全挂）

### 现象

教师端点「下载并安装」→「立即重启服务」后，页面一直转圈，最后提示服务没回来；
到服务器上看，进程已经不在了，手动再启动才恢复。

### 触发条件

Windows（或任何非 Unix）上通过教师端「立即重启」触发 `os.execv` 重启。

### 原因分析

Windows 的 `os.execv` 不是 Unix 那种「原地替换进程映像」，而是
**CreateProcess 起新进程 → 旧进程退出**，两者有一段并存窗口。

新进程启动时 `main()` 走 `PORTX.pick_port()`：

1. `is_free(port)` → 假（旧进程还在监听）；
2. `is_mine(port)` → 真（`/api/v2/ping` 返回 `service=workbench`）；
3. 返回 `state = "mine"` → `main()` 打印「已有一个本工作台实例在运行，不重复启动」并 **return**；
4. 旧进程随后也退出 → **服务彻底没了**。

### 解决措施

`/api/v2/update/restart` 在 `execv` 前：

1. `self.server.server_close()` —— 主动释放监听 socket，端口立刻空出来；
2. `os.environ["WB_RESTARTING"] = "1"` —— 给新进程留标记。

`main()` 里 `pop` 出 `restarting`：若仍判 `state == "mine"`，说明旧自己还没退干净，
等端口释放（最多 8 秒）后当作 `free` 继续启动；8 秒仍被占则保持 `mine` 退出
（说明旧进程根本没退，服务其实还在跑，绝不抢端口造两个实例）。

### 验证

- 重启前后 PID 变化：26484 → 14416；
- 旧会话失效（证明进程真的换过）；
- 服务 1 秒内恢复，版本不变；
- 另起一个实例仍被正确拦下（不会双实例抢端口）。

## P-014 · 教师端关掉签到，学生打开学习单仍被拦

**版本**：2.0.14 ｜ **日期**：2026-11-05 ｜ **严重度**：高（功能死锁）

### 现象

老师在设置里关闭「课堂签到」后，学生端今日页不再显示签到卡；但学生点学习单，
仍然弹出「请先签到 —— 今天还没有你的签到记录」，且没有任何入口可以签到。

### 原因分析

`_signed_today()` 只查考勤表当天有没有有效记录，**从不读 `CFG["checkin"]["enabled"]`**。
关闭签到 → 学生端隐藏签到卡（无法签到）→ 闸门却仍要求有记录 → 永久 403。

### 解决措施

`_signed_today()` 开头加：签到关闭即视为「没有签到要求」，直接返回 True。
学习单入口 `/g/act/<push_id>` 与资料入口 `/g/mat/<id>` 共用该函数，一处改两处生效。

### 验证

| 教师端状态 | 当天记录 | 打开学习单 |
|---|---|---|
| 无需签到 | 无 | 302 正常跳转 |
| 开启签到 | 无 | 403「请先签到」（照旧拦截） |

> 遗留：签到开关是全局配置，不是按教师账号。多教师场景下一位老师关闭会影响所有班；
> 目前两端判断标准一致不会死锁，若要做 per-teacher 需另立需求。

## P-013 · 检测得到更新，下载安装报 404

**版本**：2.0.13 ｜ **日期**：2026-11-05 ｜ **严重度**：高（无法更新）

### 原因分析

`version.json` 的 `zip` 只写了纯文件名，更新器把它拼到 manifest 所在目录（仓库根），
而包实际在 `dist/` 下。`check()` 只读 manifest、从不碰安装包，所以「检测永远成功、
安装永远 404」。

### 解决措施

- `make_release.py` / `version.json` 改写成相对仓库根的路径 `dist/<包名>.zip`；
- `updater._zip_urls()` 兼容三种写法并给出候选地址（完整 URL / 相对路径 / 老格式纯文件名），
  只有 404 才换下一个；全 404 时明确提示「安装包与 manifest 不一致」而不是笼统的地址错误。

## P-017 · 账号菜单里的设置项跳不到对应位置

**版本**：2.0.15 ｜ **日期**：2026-11-05 ｜ **严重度**：中

### 现象

左下角账号 → 菜单里点「主题与外观 / 字号 / 问候语 / 头像与昵称 / 数据导入导出」，
进入设置页后不管点哪个，都停在「外观与字号」这一屏。

### 原因分析

`settingsScrollTo()` 按 `#content .card` 的 `textContent.indexOf(关键字)` 找目标。
但「外观与字号 / 问候与好句 / 本地资料 / 数据与备份」**四个小节同属一张 `.card`**
（一个大 div 里用分隔线切开），所以四个关键字都命中同一张卡 → 只滚到这张卡的开头。

### 解决措施

- 五个小节标题挂 `data-set="theme|font|greet|nick|data"`；
- `settingsScrollTo` 优先 `querySelector('#content [data-set=...]')`，老布局才回落关键字；
- 滚动改手动算 `window.scrollTo`，偏移 = 顶栏实际高度 + 10
  （原来 `scrollIntoView(block:'start')` 会把标题压在 sticky 顶栏下）；
- 同页再点补 90ms / 320ms 两拍滚动。

### 验证

五个入口各自停在自己的小节，标题 top 70~71px（顶栏 60px），滚动位置 326 / 934 /
1106 / 1503 / 1924px，互不相同。

## P-018 · 每日一句右上角铅笔图标点击无响应

**版本**：2.0.15 ｜ **日期**：2026-11-05 ｜ **严重度**：中

### 现象

侧栏「每日一句」右上角的铅笔角标，鼠标点上去没有任何反应；
在设置页里点它更是完全无动静。

### 原因分析

`.gs-edit { pointer-events: none }` —— 点击穿透到整张 `.greet-side` 卡片上，
而整卡的 `onclick` 只做 `location.hash = '#settings'`：

- 不在设置页 → 跳过去，能滚到设置页顶部（看起来像「没弹编辑窗」）；
- 已在设置页 → hash 没变化，**浏览器什么都不做**（真正的「点了没反应」）。

### 解决措施

- `.gs-edit` 改 `pointer-events: auto` + `cursor: pointer` + 悬停底色；
- 角标自己 `event.stopPropagation()` 并直接 `openGreetSetting()` 弹浮窗；
- 补 `role="button"` + Enter/空格键支持；
- 整卡点击仍跳设置页（两个入口各司其职）。

### 验证

真实点击铅笔 → `#floatLayer` 出现且标题为「问候与好句设置」，
来源下拉、更换频率都在；已在设置页时点同样弹出。

## 附：发行包自检清单（每次发版前）

1. `python tools/make_release.py` —— 构建时已内置权限自检，失败会删包退出；
2. 计划任务 `zipperm`（`E:\wb-shots\run_zipperm.py`）—— 复查最新包的
   `create_system` / 权限 / 换行符 / UTF-8 标记；
3. `compile` —— 全部 `.py` 编译；
4. `js` —— 页面内联脚本与独立 `.js` 语法；
5. `regress` —— 53 张截图全流程；
6. 定向验收（当前版本对应的 `bNN` job）；
7. 重启正式服务，确认 `/api/v2/state` 的 `version` 已变；
8. `WbGit` 双远程推送，`ls-remote` 哈希与本地一致；
9. 远程 `version.json` 的 `sha256` 与本地 zip 一致（加 `?nocache=` 查）。
