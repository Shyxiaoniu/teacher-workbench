# 版本号维护说明

> 当前发行版本：**2.0**
> 本文用于说明版本号在项目中出现的**全部位置**，以及发版时该改哪几处、怎么验证。

---

## 一、发版时必须同步的位置

发新版时按顺序改下面 5 处，缺一处就会出现「界面显示 2.0、镜像却是别的 tag」这类不一致。

| # | 文件 | 位置 / 变量 | 当前值 | 作用 |
|---|---|---|---|---|
| 1 | `app/server.py` | 第 76 行附近 `VERSION = "2.0"` | `2.0` | **唯一代码源**。服务端 `Server` 响应头、`/api/v2/*` 的 `version` 字段、全量备份文件里的 `app_version` 都取这里 |
| 2 | `.env.example` | 末尾 `IMAGE_TAG=2.0` | `2.0` | 构建/拉取工作台镜像的 tag |
| 3 | `docker-compose.yml` | `image: ${IMAGE_REPO:-teacher-workbench}:${IMAGE_TAG:-2.0}`（**两处**：`init` 与 `workbench`） | `2.0` | compose 未提供 `.env` 时的默认 tag，改一处必须改两处 |
| 4 | `README.md` | 文首「当前版本：**2.0**」、文末「版本与许可」 | `2.0` | 对外展示的发行版本 |
| 5 | `docs/导学单数据流设计.md` | 文首「对应工作台 2.0」 | `2.0` | 设计文档对齐的版本 |

改完后可直接用一条命令核对（Linux / macOS / Git Bash）：

```bash
grep -rn --exclude-dir=.git -E 'IMAGE_TAG=|VERSION *= *"|当前版本' . | grep -v node_modules
```

## 二、不要跟着改的「版本」

下面这些也叫 version，但和发行版本无关，**发版时不要动**：

| 位置 | 含义 |
|---|---|
| `quickform/app/requirements.txt`、`.env.example` 的 `QF_IMAGE_TAG=2.5` | QuickForm 自己独立发版，节奏与本项目无关 |
| `app/core/store.py` 的 `SCHEMA_VERSION` | 数据库表结构版本，只在表结构变更时 +1 |
| `app/backup.js` 的 `VER = 3` | 备份文件格式版本，只在备份格式变更时 +1 |
| `quickform/app/app.py` 的 `'version': 1` | 提交模板字段版本 |
| 源码里 `v2.0.4`、`v2.1.0` 之类的行内注释 | 历史改动标注，保留原样即可 |

## 三、发版流程

```bash
# 1. 改完上表 5 处后，确认工作区干净
git status --short

# 2. 提交
git add -A
git commit -m "release: 2.0"

# 3. 推送到两个远程（内容保持一致）
git push github main
git push origin main

# 4. 核验两个远程指向同一个提交
git ls-remote github refs/heads/main
git ls-remote origin refs/heads/main
```

第 4 步两条输出的第一列哈希**必须相同**，否则说明有一端没推上去。

### 打 tag（可选）

```bash
git tag -a v2.0 -m "班级工作台 2.0"
git push github v2.0
git push origin v2.0
```

### 构建镜像

```bash
# 用 .env 里的 IMAGE_TAG（= 2.0）
docker compose build
docker compose up -d

# 或临时指定
IMAGE_TAG=2.0 docker compose build
```

构建完可以用接口确认容器里的版本：

```bash
curl -s http://127.0.0.1:20020/api/v2/ping
# 返回里的 "version" 应为 2.0
```

## 四、版本号规则

`主版本.次版本`，例如 `2.0`、`2.1`、`3.0`：

- **主版本**（2 → 3）：数据表结构有破坏性变更，需要按备份恢复流程迁移
- **次版本**（2.0 → 2.1）：新增功能或较大改进，数据与配置完全兼容

日常修 bug 不发新版号，直接随下一次发版合并；需要时可用三位写法的补丁号（如 `2.0.1`），
但仍以 `app/server.py` 的 `VERSION` 为准。

## 五、发行包命名与构建

发行包的版本号**不单独维护**，直接取自 `app/server.py` 的 `VERSION`：

```
班级工作台<主版本.次版本>-<yyMMdd>.zip
班级工作台2.0-261103.zip        # 版本 2.0，打包日期 2026-11-03
```

构建（脚本会自己读版本、取当天日期，并排除全部运行期数据）：

```bash
python tools/make_release.py                 # 默认输出 dist/
python tools/make_release.py --date 261103    # 指定日期
```

发版顺序建议：改版本 → 提交推送 → `python tools/make_release.py` → 把 `dist/*.zip` 发出去。
`dist/` 与 `*.zip` 均已被 `.gitignore` 忽略，不会误提交。
